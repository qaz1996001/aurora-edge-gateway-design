# ADR-0005：分階段推出與回滾策略

**狀態**：已接受  
**決策日期**：2026-Q3  
**利益相關者**：運營、產品管理、工程主管

---

## 背景

將主要重寫部署至生產是高風險。完整機隊轉換可同時級聯所有邊緣裝置的故障。我們需要策略以：
1. 在真實硬體上驗證 Rust 系統再進行全面推出
2. 早期偵測問題（在小人口上）在它們影響所有客戶前
3. 若任何事情出錯時快速回滾
4. 在轉換期間維持高可用性

---

## 決策

**在 5 個階段（Stage 0–4）分佈約 22 週部署**（Stage 0 約 1 週；Stage 1 第 1–5 週；Stage 2 第 6–9 週；Stage 3 第 10–16 週；Stage 4 第 17–22 週），每個階段皆有手動通過/不通過閘門。每個階段增加機隊涵蓋與風險。

**重要——實際推出機制**：本專案真實採用的切換機制是**二元切換**（裝置上舊堆疊全部停止、新堆疊全部啟動），搭配**人工、有文件記錄的回滾 SOP**——並非自動化百分比灰度，也不是監控閾值自動觸發回滾。本文件後續描述的自動化安全閘門與每階段告警閾值，是**規劃中的未來狀態**，而非已實施的機制。之所以列出，是因為這是我們希望演進的方向——自動化可減少值班人員所需的反應時間與判斷負擔——但目前，本專案的每一次回滾都是由人員依照下方「回滾程序」章節中記載的 SOP 執行。

---

## 階段分解

### Stage 0：啟動與基礎設施（約 1 週）

**目標**：驗證 Rust 二進制檔載入、systemd 服務啟動、基本連接工作。

**範圍**：部署 aeg-config、aeg-db（基礎服務僅限）

**風險等級**：低（無現場資料依賴；僅內部驗證）

**回滾機制**：二元切換——運營者依人工 SOP 停止 Rust 服務並啟動 Node.js 程序。目前沒有自動化金絲雀或閾值自動觸發回滾，見上方「決策」一節的說明。

**成功標準**：
- ✓ 所有服務啟動無誤
- ✓ 健康檢查通過（REST `/health` 端點回應）
- ✓ 啟動驗證期間未觀察到崩潰

---

### Stage 1：低風險服務（第 1–5 週）

**目標**：部署無狀態／低依賴服務，不涉及現場感測器資料依賴。

**範圍**：新增 aeg-led、aeg-config

**風險等級**：低

**回滾承諾**：**2 分鐘內**完整回滾至 Node.js（二元切換 + 人工 SOP）

**成功標準**：
- ✓ 指示燈控制如預期工作
- ✓ 與 Node.js 舊程式碼無衝突
- ✓ 階段期間未觀察到崩潰

---

### Stage 2：中等風險服務（第 6–9 週）

**目標**：部署有狀態服務（資料庫、感測器）搭配 I/O 副作用。

**範圍**：新增 aeg-sensors、aeg-metrics（資料庫寫入器）

**風險等級**：中

**回滾機制**：二元切換 + 人工 SOP；因本階段引入有狀態寫入器，回滾前須執行資料庫一致性檢查（`PRAGMA integrity_check`）。

**成功標準**：
- ✓ 感測器讀數與 Node.js 基線一致（透過 golden-master 比對驗證，見 ADR-0006）
- ✓ 資料庫完整性維持（PRAGMA integrity_check 通過）
- ✓ 觀察期間無遺失寫入

---

### Stage 3：高風險服務（第 10–16 週）

**目標**：部署現場資料風險最高的服務——振動、溫度等感測器資料服務——以及關鍵訊息管線（MQTT、韌體更新）。

**範圍**：新增 aeg-mqtt、aeg-ota，以及振動／溫度／感測器資料服務

**風險等級**：高——本階段是全專案風險等級最高的階段，因為涉及直接影響客戶面向產品正確性的感測器資料服務，以及韌體更新路徑。

**回滾承諾**：**3–4 分鐘內**完整回滾至 Node.js（二元切換 + 人工 SOP，含韌體更新安全檢查）

**成功標準**：
- ✓ MQTT 訊息交付在觀察負載下與 Node.js 基線一致
- ✓ OTA 韌體更新穩定成功
- ✓ 雲端連接穩定（無未預期斷開）
- ✓ 逐秒處理管線維持在預算內：端到端 p95 延遲 56.4 ms，約佔每秒處理預算的 5.6%，285 個樣本的量測中無任何週期超過 500 ms

**延長驗證**：
- 本專案至今最長的連續驗證：**10.6 小時 soak 測試，PASS**（本專案沒有 90 天或類似長時間的連續運行驗證）
- 混沌式檢查：網路故障、磁碟滿、子程序崩潰——驗證優雅恢復

---

### Stage 4：完整轉換（第 17–22 週）

**目標**：完整遷移；停用 Node.js 二進制檔。

**範圍**：部署 aeg-appserver（REST API）——本次推出中最大的單一遷移單位；停用 Node.js 程序

**風險等級**：中——就逐週期資料正確性風險而言低於 Stage 3，但是最大的單一遷移單位，因此運營／回滾風險不可忽視。

**回滾承諾**：**2–3 分鐘內**完整回滾至 Node.js（二元切換 + 人工 SOP）

**成功標準**：
- ✓ REST API 延遲在實測的每秒處理預算內：p95 56.4 ms，約佔每秒預算 5.6%，無週期超過 500 ms（見 ADR-0005 延遲量測，於 4 核 ARM Cortex-A53 目標平台上 285 個樣本的量測）
- ✓ MQTT 心跳維持（無雲端連接中斷）
- ✓ 階段期間未觀察到非計畫服務重啟
- ✓ 常駐記憶體與 CPU 使用維持在實測全端基線附近（14 個受監督服務 + Python 子行程共 206 MB 常駐；7.8 小時 soak 下 CPU 平均 6.3% / 峰值 8.8%）
- ✓ 客戶面向指標符合或超越 Node.js 基線

**推出後監控**：
- 切換後持續監控
- 若全綠：停用 Node.js 二進制檔；宣告遷移完成
- 若有問題：依人工回滾 SOP 處理；調查；可能恢復整個 Stage 4 變更

## 自動化安全閘門

每個階段皆有自動化測試，必須通過才能進入手動通過/不通過決策：

```
┌─ 程式碼審查與合併 ─┐
│                       ↓
│              CI 管線（Tier 1–3）
│              ├─ 編譯 ✓
│              ├─ 單元測試 ✓
│              ├─ 整合測試 ✓
│              └─ Marker 盤點 ✓
│                       ↓
│         ┌─ Golden-Master 測試 ─┐
│         │  ├─ 輸出對等 ✓                     │
│         │  └─ 無衰退 ✓                   │
│         └─────────────────────────────────────────┘
│                       ↓
│         ┌─ 延長 Soak 測試 ─┐
│         │  （Stage 3：10.6 小時 soak，PASS） │
│         └────────────────────────────┘
│                       ↓
│  [閘門通過] → 準備進行手動部署
│                       ↓
│  Stage 0–4 部署（需人工核准；每裝置二元切換）
│                       ↓
│  現場監控（依上方 Stage 0–4 週程表）
│                       ↓
│  通過/不通過決策（運營 + 技術主管）
│
└─────────────────────────────────────────────────────────
```

**關於自動化的說明**：上方圖中包含了期望中的自動化閘門。目前「Golden-Master 測試」以下的每個閘門都是由人員評估與執行：生產環境中沒有自動化金絲雀百分比爬升，也沒有監控閾值自動觸發回滾。我們在此列出目標狀態的自動化，是因為這是我們希望演進建構的方向——降低值班負擔與反應時間——而非因為它目前已存在。

## 回滾程序

**目前實際機制**：本專案的每一次回滾都是**二元切換**——停止 Rust 服務、啟動 Node.js 程序——由運營者依照文件化的人工 SOP 執行。目前生產環境中沒有 systemd 健康檢查自動觸發的回滾。下方指令描述的是這套人工 SOP。

**整體回滾承諾**：任何階段皆可在**5 分鐘內**完整回滾至 Node.js 堆疊。各階段量測／目標回滾時間：
- Stage 1：2 分鐘內
- Stage 3：3–4 分鐘
- Stage 4：2–3 分鐘

### 人工回滾 SOP（Stages 0–3）

```bash
# 由運營者發起；無自動觸發。運營者透過儀表板／告警觀察到問題後，
# 依文件化 SOP 執行回滾。

echo "運營者已發起回滾"

# Stage 0–1：簡單服務停止
systemctl stop aeg-led aeg-config
systemctl start node-gateway  # 恢復 Node.js

# Stage 2：回滾前 DB 一致性檢查
sqlite3 /var/lib/aeg/data.db "PRAGMA integrity_check"
if [ $? -ne 0 ]; then
  # DB 已損毀；從備份還原
  cp /var/backups/aeg/data.db.backup /var/lib/aeg/data.db
fi
systemctl stop aeg-sensors aeg-metrics
systemctl start node-gateway

# Stage 3：回滾前韌體檢查
fw_verify /var/lib/aeg/firmware/*
systemctl stop aeg-mqtt aeg-ota
systemctl start node-gateway

# 通知團隊
mail -s "Aurora Edge Gateway 已執行回滾（人工 SOP）" team@example.com \
  < <(systemctl status aeg-*.service)
```

### 手動回滾（Stage 4）

```bash
# 運營者發起回滾；目標承諾 2–3 分鐘
systemctl stop aeg-*
systemctl start node-gateway

# 驗證備用工作
curl localhost:3000/health  # 應回應
mosquitto_sub -t 'gateway/#'  # 應觀察到 MQTT 流量

# 通知客戶
status-page update "系統正在恢復；預期短暫中斷"

# 事後檢討：為何 Stage 4 失敗？
# - 回退造成問題的提交
# - 修正 Rust 程式碼中的漏洞
# - 以 golden-master 重新測試
# - 規劃重新部署
```

## 溝通計畫

### 內部（團隊）
- Stage 0–4 期間**每日站會**
- **每週風險審查**（週二下午 2 點）
- **階段結束後回顧**（找出問題；規劃下一階段）

### 外部（客戶）
- **事前公告**：「基礎設施改善即將到來」
- **Stage 2 起**：即時儀表板顯示推出進度
- **事件通知**：若執行人工回滾，5 分鐘內發出簡短訊息
- **切換後**：發行說明，記載改善內容（效能、可靠性）

## 各階段通過/不通過標準

### Stage 0 → 1 決策（Stage 0 結束時，約第 1 週）
- [ ] 啟動期間零崩潰
- [ ] 健康檢查 100% 通過率
- **決策**：**通過**，進入 Stage 1

### Stage 1 → 2 決策（第 5 週結束時）
- [ ] 指示燈控制如預期工作
- [ ] 零崩潰
- [ ] 回滾演練在 2 分鐘目標內完成
- **決策**：**通過**，進入 Stage 2

### Stage 2 → 3 決策（第 9 週結束時）
- [ ] 感測器讀數與 Node.js 基線一致（golden-master 比對）
- [ ] DB 完整性檢查通過
- [ ] 觀察到零資料遺失事件
- **決策**：**通過**，進入 Stage 3

### Stage 3 → 4 決策（第 16 週結束時）
- [ ] MQTT 訊息交付與基線一致
- [ ] OTA 更新穩定成功
- [ ] Soak 測試通過（10.6 小時連續運行，無崩潰，套用「監控與告警」一節所述的 `MALLOC_ARENA_MAX` 修正後記憶體穩定）
- [ ] 逐週期延遲在預算內：p95 56.4 ms（約佔 1 秒預算的 5.6%），無週期超過 500 ms
- [ ] 回滾演練在 3–4 分鐘目標內完成
- **決策**：**通過**，進入 Stage 4

### Stage 4 → 停用 Node.js 決策（第 22 週結束時）
- [ ] REST API 延遲在實測的每秒處理預算內（p95 56.4 ms，約佔預算 5.6%，無週期超過 500 ms）
- [ ] 常駐記憶體與 CPU 接近實測全端基線（206 MB 常駐；7.8 小時 soak 下 CPU 平均 6.3% / 峰值 8.8%）
- [ ] 零非計畫重啟
- [ ] 回滾演練在 2–3 分鐘目標內完成
- [ ] 客戶未回報重大漏洞
- **決策**：**完成**遷移；停用 Node.js

## 監控與告警

**目前狀態**：我們尚未將生產環境中的自動閾值觸發回滾接上這些告警。下方各階段指標目前由值班運營者人工觀察；告警是提示人員判斷是否執行人工回滾 SOP，而非自動觸發。我們在此列出具體閾值，作為希望建構的目標狀態。

本節的動機來自 soak 測試中的一項真實發現：在一次 7.8 小時 soak 測試期間，訊息匯流排程序出現約每小時 6.5 MB 的線性記憶體增長（45.0 MB → 95.3 MB，+112%），根因為 glibc 多執行緒 arena 增長（64 個 arena）。此問題透過設定 `MALLOC_ARENA_MAX=2` 修正；隨後的 10.6 小時 soak 測試通過，記憶體趨勢結束於約 −3.69 MB/小時。這正是長時間 soak 測試能捕捉、而短時功能測試會遺漏的衰退類型——也正是 Stage 3 延長 soak 驗證如此重要的原因。

### 各階段指標（目標狀態；閾值將隨真實現場遙測資料累積而調校）
```yaml
stage_0:
  watch:
    - service_crash_rate > 0
    - health_check_fail_rate > 5%

stage_1:
  watch:
    - service_crash_rate > 0
    - memory_growth_rate  # 注意 arena 增長型洩漏；見上方 MALLOC_ARENA_MAX 說明

stage_2:
  watch:
    - database_integrity_fail
    - sensor_reading_divergence_from_baseline

stage_3:
  watch:
    - mqtt_message_loss
    - ota_update_failure_rate
    - cloud_connectivity_drop
    - pipeline_latency_p95  # 基線：56.4 ms，約佔 1 秒預算的 5.6%

stage_4:
  watch:
    - service_crash_rate > 0
    - api_latency_p95  # 基線：56.4 ms，約佔 1 秒預算的 5.6%
    - resident_memory   # 基線：全端 206 MB
    - cpu_usage          # 基線：7.8 小時 soak 下平均 6.3% / 峰值 8.8%
```
