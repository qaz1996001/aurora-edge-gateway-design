# ADR-0001：為何要用 Rust 重寫 Aurora Edge Gateway？

**狀態**：已接受  
**決策日期**：2026-Q3  
**利益相關者**：工程團隊、產品管理、運營

---

## 背景

Aurora Edge Gateway 是工業 IoT 資料聚合平台。我們的開發與驗證硬體是 8 核 ARM aarch64、8 GB RAM 的平台——規格優渥到原始 Node.js 實施在上面看起來頗為穩定。但實際的產品目標平台受限得多：4 核 ARM Cortex-A53，標稱 4 GB RAM，但扣除 OS 之後實際可供使用者程序使用的只有約 2.84 GB，無 swap，磁碟 28 GB。這個「驗證硬體」與「產品硬體」之間的落差——而不是成本考量下的降規——才是本決策的真正觸發點。

### 硬體落差的真相

在 4 核產品平台上，對 Node.js 基線做了 3 小時活躍負載的實測：活躍進程記憶體為 **1538 MB**，約佔實際可用 2.84 GB 的 **54%**（無 swap）。CPU 使用率待機 52%、3 小時活躍後升至 64%，load average 對 4 核為 3.30。該基線以 16 個服務、8 個啟動 phase 的形式運行（實機約 20 個 OS 進程），完整開機約需 2 分 30 秒。

這個「吃掉可用記憶體 54%」的底線，幾乎沒有餘裕去吸收 Node.js 實施中既有的洩漏：

1. **記憶體洩漏嚴重性被放大**：在此平台上實測的一個 CSV 欄位擴充洩漏情境，RSS 以 **+13 MB/h** 的速率增長，約 **14 小時**後撞上每服務 500 MB 上限而自動重啟；穩態 CPU p90 隨洩漏惡化從 ~140% 升至 **169.5%**（以 4 核計）。
2. **規格優渥的硬體容易掩蓋災難性情境**：在 8 核 / 8 GB 的驗證平台上，曾捕捉到更嚴重的洩漏情境，最陡段為 **13 分鐘內 RSS +1887 MB**，導致記憶體耗盡、系統進入 thrash、餵不動看門狗，最終觸發硬體強制重置——**單日重置 98 次，約每 15 分鐘一次**。驗證硬體的餘裕掩蓋了這個情境距離災難有多近；4 核 / 約 2.84 GB 可用的產品硬體沒有這個緩衝空間。
3. **log 洪流下程序穩定性下降**：一個 log 洪流情境（20000 行中有 19997 行為重排通知）把 CPU 推到 **66.7%**，進一步壓縮剩餘的餘裕。

這三種故障模式——在 8 核 / 8 GB 驗證機上個別都可承受——一旦同一套軟體跑在 4 核 / 約 2.84 GB 可用的產品平台上，就會快速疊加成無法承受的狀況。

### 方法論信心

大規模語言遷移的可行性受到了業界近期案例的驗證。2024 年，Bun 團隊用 AI 輔助工作流執行了從 Zig 遷移至 Rust 的重大程式碼庫重寫（見 [Anthropic 官方案例研究](https://claude.com/resources/articles/ai-code-migration) 與 [GitHub PR #30412](https://github.com/oven-sh/bun/pull/30412)），完成約 75 萬行程式碼遷移，既有測試通過率達 99.8%，從第一個 commit 到合併僅耗時 11 天。這驗證了：
- 結構化 Phase A/B 方法論（忠實移植、再優化）可擴展至大型程式碼庫
- Golden-master 測試（ADR-0006）可靠地檢測行為漂移，而單元測試獨立無法做到
- 多代理並行工作流加速遷移速度，同時減少審查瓶頸

這個案例直接影響了我們對本專案時程（Stage 0–4，合計約 22 週）與驗證策略的信心評估。

---

## 決策

**用 Rust 重寫 Aurora Edge Gateway**，使用漸進式 Phase A/B 策略搭配分階段生產推出（見 ADR-0005、ADR-0006）。

---

## 理由

### 為何選擇 Rust？

**記憶體安全設計**
- Rust 的型別系統在編譯時消除未定義行為、記憶體洩漏和資料競爭
- 無垃圾回收器 → 無 GC 暫停阻擋感測器讀取
- 透過 drop trait 進行明確資源管理 → 保證清理
- **結果**：記憶體行為可預測；無神秘的記憶體不足崩潰

**確定性效能**
- 無 stop-the-world GC 暫停 → 高峰負載下無尾延遲突刺
- 所有並行明確（無隱藏事件迴圈隱藏問題）
- 編譯器強制明確處理錯誤
- **結果**：延遲變得有界且可分析；峰值效能可預測

**優秀效能廣度**
- 零成本抽象（編譯為機器碼，無直譯器開銷）
- Async/await 最小開銷（tokio 執行時）
- 細粒度配置控制（標準庫無隱藏配置）
- **結果**：受限硬體上有效率的資源利用；CPU 廣度用於未來功能

**卓越物聯網/系統生態系**
- `tokio`：高並行工作負載的業界標準非同步執行時
- `rumqttc`：成熟 MQTT 用戶端庫（async-first、IoT 優化）
- `rusqlite`：同步 SQLite 綁定（邊緣使用案例足夠，無需非同步複雜性）
- `axum`：現代 HTTP 框架（零成本路由、型別安全）
- `serde`：零複製序列化
- **結果**：所有必要技術成熟且良好整合

---

### 考量的替代方案

#### 選項 A：「增加更多記憶體」（Node.js + Clustering）
- **方法**：執行多個 Node.js 程序；新增快取；增加記憶體限制
- **優點**：更低工程努力（無重寫）；利用現有程式碼
- **缺點**：
  - 遮掩根本原因（每個程序中仍存在記憶體洩漏）
  - 增加每個裝置佔用量（受限硬體上不可行）
  - 無法解決尾延遲或穩定性問題
- **決策**：拒絕 — 臨時創可貼；不解決根本約束

#### 選項 B：Go（編譯替代方案）
- **方法**：用 Go 重寫（學習曲線比 Rust 更低）
- **優點**：團隊快速上手；編譯；良好並行（goroutines）
- **缺點**：
  - 仍有垃圾回收（根本上無法解決記憶體洩漏）
  - 並行除錯比 Rust 的明確模型更難
  - IoT/邊緣生態系比 Rust 小
- **決策**：拒絕 — 無法消除根本記憶體問題；對受限硬體不夠理想

#### 選項 C：C++（最大效能）
- **方法**：用 C++ 重寫（最大控制、最大效能）
- **優點**：絕對最大效能；細粒度記憶體控制
- **缺點**：
  - 陡峭學習曲線；記憶體安全負擔仍落在團隊身上
  - 引入新漏洞的風險較高
  - 建置系統複雜
  - 開發速度較慢
- **決策**：拒絕 — 過度複雜；Rust 達成安全目標更清晰

#### 選項 D：Rust（已選擇） ✅
- **方法**：完整用 Rust 重寫，搭配分階段推出
- **優點**：
  - 設計上消除記憶體洩漏
  - 效能等同 C++，無安全負擔
  - 卓越非同步/並行原語
  - 豐富的物聯網生態系
  - 團隊學習有價值的系統程式設計語言
  - 強大的編譯時保證降低生產問題
- **缺點**：
  - 較高的前期工程努力（Stage 0–4 合計約 22 週）
  - 團隊新語言上手（2–3 週）
  - 較長的初始開發時間軸
- **決策**：已選擇 — 最佳長期投資；解決記憶體洩漏與確定性問題

## 結果

### 正面
1. **記憶體佔用大幅下降**：在產品硬體上同口徑比較，全棧常駐記憶體從 **1538 MB**（Node.js，3 小時活躍負載）降到 **206 MB**（Rust，14 個受監督服務 + Python 子行程的全棧）——在 4 核產品平台約 2.84 GB 可用記憶體下留出了真正的餘裕。
2. **CPU 與 load 大幅下降**：Node.js 於 3 小時活躍負載後實測 **CPU 64%**、load average **3.30/4 核**；Rust 重寫版本於 7.8 小時 soak 測試中實測 **CPU 平均 6.3% / 峰值 8.8%**、**load average 平均 0.50 / 峰值 1.81**——測試時長與硬體等級相當。
3. **延遲變得有界且微小**：逐秒管線取樣 285 個樣本，p95 為 **56.4 ms**、p99 為 **57.7 ms**，p95 僅佔每秒預算的約 **5.6%**，且**零**樣本超過 500 ms。
4. **重啟模式提早穩定**：soak 測試中 3 次重啟集中在前 66 分鐘，之後 **6.7 小時零重啟**——與 Node.js 基線約每 14 小時一次的重啟週期、以及驗證硬體事故中約每 15 分鐘一次的重置節奏，是完全不同的故障形態。
5. **降低維護負擔**：更簡單的告警規則；真正發生問題時根本原因更清晰
6. **團隊成長**：工程師學習系統程式設計語言；對未來專案有轉移價值

### Soak 測試中發現的記憶體增長——以及它真正的根本原因
Rust 的編譯期保證消除的是特定一類錯誤（use-after-free、資料競爭、懸掛指標）——它並不保證系統完全不會有記憶體增長，而重寫後系統的 soak 測試在實務上證實了這個區別。

一次 7.8 小時的 soak 測試捕捉到訊息匯流排進程從 **45.0 MB 增長到 95.3 MB（+112%）**——速率約 **6.5 MB/h** 的線性趨勢，這種斜率放在儀表板上看起來就跟真正的洩漏一模一樣。

根因追查發現，這並非 Rust 記憶體安全錯誤，而是 **glibc 多執行緒配置器的 arena 行為**：在預設每執行緒 arena 數可擴張至 64 個的情況下，訊息匯流排進程的執行緒與配置模式導致其總映射 arena 記憶體隨時間擴張，與任何 Rust 層級的洩漏配置無關。

修復方式是一個環境變數設定——**`MALLOC_ARENA_MAX=2`**——限制 glibc 的 arena 數量上限。後續一次 **10.6 小時 soak 測試**驗證了修復效果：RSS 先升至約 24.5 MB，再回落至 **17.2 MB**，增長斜率由前 2 小時的 **+5.74 MB/h**、轉為中段的 **0.00 MB/h**、再到末 2 小時的 **−3.69 MB/h**——**PASS**。

**這個事件驗證的洞見是**：改用 Rust 消除的是語言層的記憶體安全錯誤，但不會自動消除配置器或執行環境設定層級引入的記憶體增長。這類問題對型別系統是不可見的，只有靠長時間 soak 測試才能被發現——這正是為何 soak 測試在重寫完成後仍留在驗證計畫裡，而不只是 Node.js 時代才需要的手段。

### 負面
1. **開發時間**：約 22 週的重寫與分階段上線（Stage 0–4）（vs. Node.js 上的持續修補）
2. **團隊學習曲線**：Rust 借用檢查器、生命週期、async/await 陌生（2–3 週上手）
3. **雙重維護**：推出期間必須支援兩個系統（約 22 週的工程開銷）
4. **推出風險**：重寫總是面臨行為漂移風險（透過 golden-master 測試、分階段推出緩解）

### 接受的取捨
- **短期工程努力**（約 22 週的開發與推出、2–3 週訓練）換取**長期運營心安**
- **開發複雜性**（學習新語言）換取**消除記憶體相關生產問題**

## 驗證

### 我們如何知道此決策有效
1. **Phase A**（忠實搬遷）：Golden-master 測試驗證與 Node.js 基線的行為等價性
2. **Phase B**（強化）：在產品等級硬體上進行 soak 測試，揪出並修復如上述 glibc arena 增長這類問題
3. **分階段推出**（Stage 0–4，合計約 22 週）：每個階段在生產裝置上驗證；偵測到問題時可在整體 5 分鐘內（各階段 2–4 分鐘）回滾
4. **生產觀察**：目前完成過的最長連續 soak 測試為 **10.6 小時**（`MALLOC_ARENA_MAX` 修復驗證那次），結果為 PASS；我們尚未累積 90 天的現場資料，也不做此宣稱

### 成功指標（實測結果）
- ✓ 全棧常駐記憶體：**206 MB** vs Node.js **1538 MB**（同等產品硬體，3 小時活躍負載）
- ✓ CPU：**平均 6.3% / 峰值 8.8%**（7.8 小時 soak）vs Node.js **64%**（3 小時活躍）；load average **平均 0.50 / 峰值 1.81** vs **3.30**
- ✓ 逐秒管線延遲：p95 **56.4 ms** / p99 **57.7 ms**，p95 僅佔每秒預算約 **5.6%**，285 個樣本中**零**筆超過 500 ms
- ✓ 目前通過的最長 soak 測試：**10.6 小時**，於套用 `MALLOC_ARENA_MAX=2` 修復後，末段斜率 −3.69 MB/h
- ✓ 分階段推出計畫（Stage 0–4，約 22 週），可於 5 分鐘內完成回滾
- ✓ 團隊能獨立維護與增強（Phase A 後）
