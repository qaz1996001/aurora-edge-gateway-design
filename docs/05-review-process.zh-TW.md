# 審查流程：多角色結構化程式碼審查

大型重寫的程式碼審查必須捕捉跨領域問題（安全性、效能、記憶體安全、架構一致性）。本文檔描述一個**多角色審查框架**，每個審查者有特定的視角和責任。

---

## 審查角色與責任

### 角色 1：Rust 專家

**責任**：確保慣用 Rust；捕捉記憶體安全和生命週期問題；驗證型別安全保證。

**檢查清單**：
- [ ] 程式碼使用 Rust 慣例（無 C 風格迴圈、手動生命週期管理）
- [ ] 所有 `unsafe` 區塊以 `SAFETY:` 註釋標註
- [ ] 無 unwrap()/panic!() 在生產程式碼路徑中
- [ ] 使用正確的錯誤型別
- [ ] 生命週期正確；無不必要的 `.clone()`
- [ ] 編譯器警告已解決

---

### 角色 2：安全工程師

**責任**：識別安全漏洞（injection、buffer overflow、密碼學濫用）。

**檢查清單**：
- [ ] 所有使用者輸入在使用前驗證
- [ ] 無 SQL injection（使用參數化查詢）
- [ ] 無命令 injection
- [ ] 密碼操作使用標準庫
- [ ] 無硬編碼祕密
- [ ] 檔案操作安全（無路徑遍歷）

---

### 角色 3：系統架構師

**責任**：驗證架構一致性；確保模組邊界尊重；檢查跨領域問題。

**檢查清單**：
- [ ] 模組責任清晰；單一關切點
- [ ] 依賴遵循無環依賴圖
- [ ] 服務間通訊使用已記錄的協議
- [ ] 並行模型清晰
- [ ] 非同步/等待邊界明確
- [ ] 錯誤傳播一致

---

### 角色 4：效能工程師

**責任**：識別效能瓶頸；捕捉配置/GC 問題；驗證效能目標。

**檢查清單**：
- [ ] 關鍵路徑使用高效資料結構
- [ ] 迴圈中無不必要的配置
- [ ] 複製/複製最小化
- [ ] 鎖競爭最小化
- [ ] 緩衝策略適當
- [ ] 零複製模式在適用時使用

---

### 角色 5：程式碼審查者

**責任**：確保程式碼可測試、可維護、可讀；驗證測試涵蓋率。

**檢查清單**：
- [ ] 程式碼可測試
- [ ] 所有邏輯都有單元測試（70%+ 涵蓋率）
- [ ] 測試涵蓋 happy path 和錯誤情況
- [ ] 測試名稱描述性強
- [ ] 註釋解釋「為什麼」，不是「什麼」
- [ ] 無死程式碼

---

## 審查工作流程

### 步驟 1：自我審查（開發者）
開發者在提交前自我審查所有 5 個檢查清單。

**輸出**：自我審查清單附加到 PR。

### 步驟 2：非同步審查（5 位審查者平行）
所有 5 位審查者同時提供回饋（24h 周轉）。

**輸出**：每位審查者提供：
- 特定行的註釋
- 嚴重性等級（🚨 必須修正；⚠️ 應該修正；💡 最好修正）
- 可實行的修正建議

### 步驟 3：開發者回應
開發者回應所有回饋：
- **🚨**：全部解決
- **⚠️**：修正或記錄理由
- **💡**：修正或用 `TODO(port)` 標記為 Phase B 延遲

**輸出**：更新的 PR + 對每條註釋的回應。

### 步驟 4：驗證審查（抽查）
一位審查者（輪流）確認回饋已真正解決。

### 步驟 5：合併 & 迴歸測試
- PR 合併到 main
- CI/CD 管道執行
- 若測試失敗：調查；修正；重新測試
- 若測試通過：程式碼已準備好

## 審查 SLA

| 角色 | 周轉時間 |
|---|---|
| Rust 專家 | 24 小時 |
| 安全工程師 | 24 小時 |
| 架構師 | 24 小時 |
| 效能工程師 | 48 小時 |
| 程式碼審查者 | 24 小時 |

---

## 自動化

這些可由 CI/CD 檢查，無需人工審查：
- `cargo fmt`（格式化）
- `cargo clippy`（Lint）
- `cargo test`（單元測試）
- `cargo tarpaulin`（程式碼涵蓋率 ≥ 70%）
- `cargo audit`（無已知漏洞）
