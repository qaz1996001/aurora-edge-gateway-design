# 風險登記：分類與管理

本文檔定義了 Node.js → Rust 遷移期間如何識別、分類、追蹤和緩解風險。共享風險分類確保整個團隊溝通一致。

---

## 風險分類

### 分類 1：技術風險

品質、正確性或效能相關的風險。

**範例**：
- 行為對等性未達成（Rust 輸出不同於 Node.js）
- 效能目標未達（例如：端到端逐週期延遲明顯超出既定基線——p95 56.4 ms，約佔每秒處理預算的 5.6%，於 4 核 ARM Cortex-A53 目標平台量測——或常駐記憶體明顯超出 14 個受監督服務 + Python 子行程共 206 MB 的實測全端基線）
- 記憶體洩漏（unsafe 區塊濫用或循環參照在 Arc/Rc 中）
- 資料庫損毀（SQLite PRAGMA integrity_check 失敗）

---

### 分類 2：運營風險

部署、監控和回滾相關的風險。

**範例**：
- 回滾程序不工作
- 指標/監控缺失
- 自動安全閥失敗
- systemd 服務配置錯誤

---

### 分類 3：知識風險

團隊專業知識和知識轉移相關的風險。

**範例**：
- 團隊缺乏 Rust 專業知識
- 關鍵人員離職
- 程式碼文件不足
- 團隊培訓不足

---

### 分類 4：外部風險

外部因素（依賴、生態系、第三方）。

**範例**：
- 依賴漏洞（rumqttc、tokio 有安全問題）
- 生態系不成熟（某 crate 無人維護）
- 客戶回饋揭示未預期的使用案例
- 硬體不相容

---

## 風險嚴重性等級

### 🔴 CRITICAL
**影響**：生產停機或資料喪失

**恢復時間**：> 2 小時

**Go/No-Go 閘門**：必須在 Stage 3 前解決

---

### 🟠 HIGH
**影響**：服務不可用或嚴重衰退

**恢復時間**：1–2 小時

**Go/No-Go 閘門**：必須在 Stage 2 前解決

---

### 🟡 MEDIUM
**影響**：部分功能喪失或資源衰退

**範例**：CPU 使用漂移到 > 75，餘裕 < 10%

**Go/No-Go 閘門**：應在 Stage 1 前解決

---

### 🟢 LOW
**影響**：次要問題或技術債

**Go/No-Go 閘門**：可在 Phase B 解決

---

## 風險管理流程

### 步驟 1：風險識別（持續）
- 程式碼審查期間：審查者標記潛在問題
- 測試失敗：異常記錄為風險
- 架構審查：已知難題主動識別

### 步驟 2：風險評估（24 小時內）
團隊主管評估：
- **機率**：多可能發生？（0–100%）
- **影響**：若發生，結果有多糟？
- **嚴重性**：結合機率+影響，指派嚴重性等級

### 步驟 3：風險緩解（立即後）
定義具體緩解步驟，指派所有人和截止日期。

### 步驟 4：風險追蹤（週度）
- **週二風險同步**（30 分）：審查所有開放風險
- **狀態更新**：所有人匯報進度
- **升級**：若截止日期有風險，升級至團隊主管

### 步驟 5：風險解決（完成時）
確認緩解完成（含證據），更新狀態為已解決。

## 範例：風險 RISK-001

| 欄位 | 值 |
|---|---|
| **風險 ID** | RISK-001 |
| **分類** | 技術（正確性） |
| **嚴重性** | 🔴 CRITICAL |
| **標題** | 行為對等性：感測器聚合 ±1% 誤差 |
| **描述** | Rust 感測器聚合算法產生不同值（例如 230.5V vs. 234.2V）。違反 Phase A 要求「100% 行為等價」。 |
| **機率** | 35%（已知：浮點精度是問題） |
| **影響** | Phase A golden-master 測試完全失敗；專案受阻 |
| **緩解** | <ul><li>逐行從 Node.js 移植算法</li><li>使用相同浮點精度（f64）</li><li>單元測試比對 golden 資料集</li></ul> |
| **狀態** | 🟡 進行中（Phase A 第 4 週） |
| **所有人** | Jane（感測器模組主管） |
| **創建** | 2026-09-15 |
| **截止** | 2026-10-10 |

## 已知風險（示例）

### 技術範例
1. **浮點精度損失**：感測器讀數（電壓、電流）在 Rust 中計算精度略異 → 影響 0.01% 讀數 → LOW；用 golden-master 測試容差緩解

2. **Async 死鎖**：tokio 任務試圖以不同順序獲得兩個鎖 → 負載下可能死鎖 → HIGH；用顯式鎖排序 + 壓力測試緩解

## 範例：風險 RISK-013

| 欄位 | 值 |
|---|---|
| **風險 ID** | RISK-013 |
| **分類** | 運營（磁碟／儲存） |
| **嚴重性** | 🟠 HIGH |
| **標題** | WAV 錄製與服務日誌造成磁碟成長 |
| **描述** | 目標平台（28 GB 總磁碟）上 WAV 累積約每 3 小時 +3.8 GB（約 30 GB/日）。一次 7.8 小時 soak 測試中，訊息匯流排服務的單一日誌檔達 914 MB，感測器資料服務日誌同期達 203 MB。修正前，磁碟清理作業約每 1.3 小時觸發一次（每日約 18 次），顯示磁碟填滿速度快到需要非常頻繁的介入。 |
| **機率** | 100%（soak 測試中實際觀察到，非假設性風險） |
| **影響** | 磁碟耗盡會中止 WAV 錄製及／或日誌記錄；在 28 GB 磁碟、約 30 GB/日 WAV 成長速度下，若無清理機制，約一天內即可耗盡可用空間。 |
| **緩解** | <ul><li>調整磁碟清理頻率與保留策略，使清理按可預期排程執行而非被動觸發（修正後觀察到約每 7 小時一次、每日約 3.4 次）</li><li>對訊息匯流排與感測器資料服務日誌設上限或輪替</li><li>將磁碟剩餘空間趨勢列為 soak 測試的一級指標，而非僅看崩潰/未崩潰</li></ul> |
| **狀態** | 🟢 已解決（清理頻率已修正；於後續 soak 測試中持續監控） |
| **所有人** | 平台團隊 |
| **創建** | 2026-09-xx |
| **截止** | 已完成 |

## 範例：風險 RISK-014

| 欄位 | 值 |
|---|---|
| **風險 ID** | RISK-014 |
| **分類** | 技術（記憶體、執行時） |
| **嚴重性** | 🟠 HIGH |
| **標題** | 訊息匯流排程序的 glibc 多執行緒 Arena 膨脹 |
| **描述** | 即使使用 Rust，訊息匯流排程序在一次 7.8 小時 soak 測試中仍出現約 6.5 MB/小時的線性記憶體增長（45.0 MB → 95.3 MB，+112%）。根因是 glibc 多執行緒 malloc arena 行為（64 個 arena），並非 Rust 層級的洩漏（未涉及 `unsafe` 濫用或 `Arc`/`Rc` 循環參照）。這提醒我們「用 Rust 寫」並不能自動排除原生配置器層級的記憶體增長問題。 |
| **機率** | 100%（soak 測試中直接觀察到） |
| **影響** | 若不緩解，此增長模式最終會在長時間邊緣部署中使訊息匯流排程序效能下降或崩潰；只有數小時等級的 soak 測試才能發現此問題——短時間功能測試無法發現。 |
| **緩解** | <ul><li>設定 `MALLOC_ARENA_MAX=2` 以限制 glibc arena 數量</li><li>重新執行 soak 測試確認：後續 10.6 小時 soak 測試通過，記憶體趨勢末段約為 −3.69 MB/小時</li><li>將數小時等級的 soak 測試（而非僅短時間功能測試）列為任何引入新長駐服務階段前的標準閘門（見 ADR-0005 Stage 3）</li></ul> |
| **狀態** | 🟢 已解決（已透過 10.6 小時 soak 測試驗證修正） |
| **所有人** | 平台團隊 |
| **創建** | 2026-09-xx |
| **截止** | 已完成 |
