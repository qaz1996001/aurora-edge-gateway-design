# 風險登記：分類與管理

## 概覽

本文件定義了 Node.js → Rust 遷移期間風險如何被識別、分類、追蹤與緩解。共用的風險分類確保整個團隊溝通一致。

---

## 風險分類

### 分類 1：技術風險（品質、正確性、效能）
與程式碼品質、架構正確性或效能目標相關的風險。

**範例**：
- 行為對等性未達成（Rust 輸出不同於 Node.js）
- 效能目標未達（例如：端到端逐週期延遲明顯超出既定基線——p95 56.4 ms，約佔每秒處理預算的 5.6%，於 4 核 ARM Cortex-A53 目標平台量測——或常駐記憶體明顯超出 14 個受監督服務 + Python 子行程共 206 MB 的實測全端基線）
- Rust 的記憶體洩漏（unsafe 區塊誤用或 Arc/Rc 中的循環參照）
- 資料庫損毀（SQLite PRAGMA integrity_check 失敗）

---

### 分類 2：運營風險（部署、監控、回滾）
與部署、上線推展、運營準備度相關的風險。

**範例**：
- 回滾程序無法運作（無法快速還原 Node.js）
- 指標／監控缺失（無法在生產環境中偵測問題）
- 自動化安全閥失效（測試通過但實際行為錯誤）
- systemd 服務設定錯誤（服務無法啟動）

---

### 分類 3：知識風險（團隊專業知識、文件）
與團隊能力及知識傳承相關的風險。

**範例**：
- 團隊缺乏 Rust 專業知識（不熟悉 tokio、async/await、借用檢查器）
- 關鍵人員於遷移期間離職
- 程式碼缺乏文件（日後難以除錯）
- 培訓不足（團隊對於上線後維護 Rust 程式碼沒有信心）

---

### 分類 4：外部風險（依賴、生態系、第三方）
超出團隊控制範圍的外部因素相關風險。

**範例**：
- 依賴漏洞（rumqttc、tokio、rusqlite 存在安全性問題）
- 生態系不成熟（某個 crate 無人維護或不穩定）
- 客戶回饋揭示未預期的使用情境（Node.js 中隱藏的行為）
- 硬體不相容（Rust 執行檔在特定 ARM 變體上無法運作）

---

## 風險嚴重性等級

### 🔴 CRITICAL
**影響**：生產環境停機或資料遺失

**範例**：遷移期間資料庫損毀；無法恢復客戶資料

**恢復時間**：> 2 小時

**Go/No-Go 閘門**：必須在 Stage 3（中風險服務部署）前解決

---

### 🟠 HIGH
**影響**：服務無法使用或嚴重衰退

**範例**：記憶體洩漏導致裝置在 2 天後當機；需要手動重新啟動

**恢復時間**：1–2 小時

**Go/No-Go 閘門**：必須在 Stage 2（有狀態服務部署）前解決

---

### 🟡 MEDIUM
**影響**：部分功能喪失或資源衰退

**範例**：持續負載下 CPU 使用率漂移到 > 75%，餘裕低於 10%

**恢復時間**：30 分鐘 – 2 小時

**Go/No-Go 閘門**：應在 Stage 1 前解決；若延後，必須有替代方案

---

### 🟢 LOW
**影響**：次要的使用者端問題或技術債

**範例**：LED 顏色與預期 RGB 值略有偏差；文件不完整

**恢復時間**：< 30 分鐘

**Go/No-Go 閘門**：可在 Phase B 處理；不阻擋上線推展

## 風險管理流程

### 步驟 1：風險識別（持續進行）
- **程式碼審查期間**：審查者標記潛在問題（`⚠️ 這看起來有風險...`）
- **測試期間**：測試失敗或異常記錄為風險
- **架構審查期間**：主動識別已知的難題

### 步驟 2：風險評估（24 小時內）
團隊主管（或風險所有人）評估：
- **機率**：此風險發生的可能性有多高？（0–100%）
- **影響**：若發生，後果有多嚴重？
- **嚴重性**：結合機率 + 影響，指派嚴重性等級（CRITICAL / HIGH / MEDIUM / LOW）

### 步驟 3：風險緩解（評估完成後立即進行）
- 定義具體的緩解步驟（不是「小心一點」這類空話——而是明確的行動）
- 指派所有人與截止日期
- 更新風險登記表

### 步驟 4：風險追蹤（每週）
- **週二風險同步會議**（30 分鐘）：審查所有未結案風險
- **狀態更新**：所有人回報緩解進度
- **升級**：若截止日期有風險，升級給團隊主管

### 步驟 5：風險解決（完成時）
- 所有人確認緩解已完成（附證據：測試結果、程式碼審查核准）
- 更新狀態為 ✅ 已解決
- 將風險存檔至歷史登記表

## 風險升級程序

### 若風險無法於截止日期前解決

1. **通知團隊主管**（錯過截止日期當天）
2. **重新評估嚴重性**（若適當——可能比最初認為的不那麼關鍵）
3. **選擇解決方案**：
   - **方案 A**：延後至 Phase B（在程式碼中以 TODO(port) 記錄）
   - **方案 B**：實作替代方案（例如：停用功能、加入斷路器）
   - **方案 C**：暫停該 Stage；調查根因

**範例**：RISK-012（指示燈序列埠時序）未能於原定截止日期前解決；由於影響僅為連線初期的短暫延遲（LOW 嚴重性），決定延後至 Phase B。

## 已知風險

以下是這次重寫實際追蹤的風險，專案與裝置名稱已匿名化。其中大多數從未發生——這正是風險登錄簿的用途；真的發生過的，已連結到上方對應條目。

### 技術風險
1. **浮點精度損失**：感測器讀數（電壓、電流）在 Rust 與 Node.js 中計算精度略有不同 → 影響 0.01% 的讀數 → LOW 嚴重性；透過在 golden-master 測試中接受容差來緩解

2. **Async/Await 死鎖**：Tokio 任務嘗試以與 Node.js 事件迴圈不同的順序取得兩個鎖 → 負載下可能發生死鎖 → HIGH 嚴重性；透過明確的鎖排序規範與壓力測試緩解

3. **配置器層級的記憶體增長**：長駐服務即使應用程式碼沒有洩漏，也會在配置器內累積已保留但未使用的記憶體 → RSS 逐漸增長 → MEDIUM 嚴重性；透過 soak 測試與配置器調校緩解。此風險已實際發生過一次——詳見 RISK-014

### 運營風險
1. **缺乏回滾工具**：沒有自動化程序可從 Rust 切回 Node.js → 手動恢復可能耗時數小時 → HIGH 嚴重性；透過每週測試回滾程序緩解

2. **監控缺口**：新 crate 缺少 Prometheus 指標 → 在客戶回報之前看不到效能問題 → MEDIUM 嚴重性；透過在審查清單中強制要求指標緩解

### 知識風險
1. **Rust 編譯器學習曲線**：團隊需要 4 週以上才能理解借用檢查器 → 開發速度比預估慢 → MEDIUM 嚴重性；透過結對編程、文件審查、培訓課程緩解

2. **關鍵人員依賴**：只有一位工程師完全理解 async/tokio 架構 → 若此人離職，程式碼庫將面臨風險 → HIGH 嚴重性；透過記錄架構文件、讓多位審查者參與 async 相關程式碼緩解

## 風險驗收與簽核

### 每個 Stage 部署前

**風險審查委員會**（技術主管、架構師、運營主管）召開會議以：
1. 審查所有 **CRITICAL** 與 **HIGH** 嚴重性風險 → 必須已解決，或以書面明確驗收
2. 確認 **MEDIUM** 嚴重性風險已有緩解措施或可接受的替代方案
3. 驗收 **LOW** 嚴重性風險，或延後至 Phase B
4. **簽核**：「我們接受剩餘風險，並核准部署至 Stage X」

**簽核範例**：
```
Stage 3（中風險服務）風險審查
日期：2026-10-15
```
