# 風險登記：分類與管理

本文檔定義了 Node.js → Rust 遷移期間如何識別、分類、追蹤和緩解風險。共享風險分類確保整個團隊溝通一致。

---

## 風險分類

### 分類 1：技術風險

品質、正確性或效能相關的風險。

**範例**：
- 行為對等性未達成（Rust 輸出不同於 Node.js）
- 效能目標未達（CPU > 70%，記憶體 > 1600 MB）
- 記憶體洩漏（unsafe 區塊濫用或循環參照在 Arc/Rc 中）
- 資料庫損毀（SQLite PRAGMA integrity_check 失敗）

---

### 分類 2：運營風險

部署、監控和回滾相關的風險。

**範例**：
- 回滾程序不工作
- 指標/監控缺失
- 自動安全閥失敗
- systemd 服務配置錯誤

---

### 分類 3：知識風險

團隊專業知識和知識轉移相關的風險。

**範例**：
- 團隊缺乏 Rust 專業知識
- 關鍵人員離職
- 程式碼文件不足
- 團隊培訓不足

---

### 分類 4：外部風險

外部因素（依賴、生態系、第三方）。

**範例**：
- 依賴漏洞（rumqttc、tokio 有安全問題）
- 生態系不成熟（某 crate 無人維護）
- 客戶回饋揭示未預期的使用案例
- 硬體不相容

---

## 風險嚴重性等級

### 🔴 CRITICAL
**影響**：生產停機或資料喪失

**恢復時間**：> 2 小時

**Go/No-Go 閘門**：必須在 Stage 3 前解決

---

### 🟠 HIGH
**影響**：服務不可用或嚴重衰退

**恢復時間**：1–2 小時

**Go/No-Go 閘門**：必須在 Stage 2 前解決

---

### 🟡 MEDIUM
**影響**：部分功能喪失或資源衰退

**範例**：CPU 使用漂移到 > 75，餘裕 < 10%

**Go/No-Go 閘門**：應在 Stage 1 前解決

---

### 🟢 LOW
**影響**：次要問題或技術債

**Go/No-Go 閘門**：可在 Phase B 解決

---

## 風險管理流程

### 步驟 1：風險識別（持續）
- 程式碼審查期間：審查者標記潛在問題
- 測試失敗：異常記錄為風險
- 架構審查：已知難題主動識別

### 步驟 2：風險評估（24 小時內）
團隊主管評估：
- **機率**：多可能發生？（0–100%）
- **影響**：若發生，結果有多糟？
- **嚴重性**：結合機率+影響，指派嚴重性等級

### 步驟 3：風險緩解（立即後）
定義具體緩解步驟，指派所有人和截止日期。

### 步驟 4：風險追蹤（週度）
- **週二風險同步**（30 分）：審查所有開放風險
- **狀態更新**：所有人匯報進度
- **升級**：若截止日期有風險，升級至團隊主管

### 步驟 5：風險解決（完成時）
確認緩解完成（含證據），更新狀態為已解決。

|---|---|
| **風險 ID** | RISK-001 |
| **分類** | 技術（正確性） |
| **嚴重性** | 🔴 CRITICAL |
| **標題** | 行為對等性：感測器聚合 ±1% 誤差 |

| **緩解** | <ul><li>逐行從 Node.js 移植算法</li><li>使用相同浮點精度（f64）</li><li>單元測試比對 golden 資料集</li></ul> |
| **狀態** | 🟡 進行中（Phase A 第 4 週） |
| **所有人** | Jane（感測器模組主管） |
| **創建** | 2026-09-15 |
| **截止** | 2026-10-10 |

## 已知風險（示例）

### 技術範例
1. **浮點精度損失**：感測器讀數（電壓、電流）在 Rust 中計算精度略異 → 影響 0.01% 讀數 → LOW；用 golden-master 測試容差緩解

2. **Async 死鎖**：tokio 任務試圖以不同順序獲得兩個鎖 → 負載下可能死鎖 → HIGH；用顯式鎖排序 + 壓力測試緩解
