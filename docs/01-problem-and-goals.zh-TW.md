# 問題陳述與目標：為何用 Rust 重寫 Aurora Edge Gateway？

## 執行摘要

**Aurora Edge Gateway** 是一個分散式工業 IoT 平台，負責邊緣設備上的實時感測器資料聚合、邊側計算和設備控制。原始 Node.js 實現雖然功能完整，但在生產環境中暴露出三個關鍵弱點，威脅可靠性與可擴展性：

1. **記憶體洩漏**：長時間運行的感測器管道有可觀察的多日運行時間衰退
2. **高 CPU 開銷**：高峰期感測器事件處理時尾部延遲 > 100ms（8 核 ARM）
3. **不可預測的崩潰**：連續負載運行 7–14 天後無故崩潰

本文檔概述了完全用 Rust 重寫的商業與技術理由、可量化的目標，以及權衡。

## 問題：Node.js 的瓶頸

### 症狀 1：連續負載下記憶體洩漏
- **觀察**：現場部署的邊緣閘道器在正常運行下每天顯示 ~2% 的記憶體增長
- **影響**：256 MB 設備會在 ~7 天後變得不穩定；需要手動重啟
- **根本原因**：事件流聚合迴圈中的循環參照；垃圾回收暫停無法完全回收記憶體
- **嘗試過的修復**：切換 GC 策略、添加手動清理代碼 → 暫時緩解，但根本問題依然

### 症狀 2：高峰負載期間尾部延遲尖峰
- **觀察**：95th-percentile 事件處理延遲：**85–120 ms**（目標：< 10 ms）
- **影響**：實時感測器觸發（例如設備報警閾值）錯過緊密回應期限
- **根本原因**：
  - Node.js 事件迴圈在高並行 MQTT 消息突增期間競爭
  - V8 JIT 編譯首次執行代碼路徑的開銷
  - 垃圾回收暫停（100–500 ms）阻塞感測器讀取
- **嘗試過的修復**：Worker 線程、叢集化、async/await 重構 → 部分改善，但架構極限已達

### 症狀 3：不可解釋的進程崩潰
- **觀察**：連續運行 7–14 天後閘道器無日誌崩潰
- **根本原因**：可能是深層嵌套異步調用鏈中的堆棧溢出；在生產環境中難以診斷
- **影響**：每個事件 15–20 分鐘停機時間；緩衝的感測器資料丟失

## 商業目標

### 主要目標
1. **消除記憶體洩漏**：在 30 天連續運行中達到零計畫外重啟
2. **降低延遲尾部**：95th-percentile 事件處理延遲 < 10 ms（即使在高峰感測器突增期間）
3. **提升運營穩定性**：支援 90+ 天連續運行，無需人工干預

### 次要目標
1. **降低 CPU 佔用率**：邊緣設備上功耗降低（與電池備用或熱限制相關）
2. **簡化除錯**：確定性行為與編譯時檢查減少生產事件
3. **支持未來擴展**：為感測器數量 10 倍增長做準備，無需重新設計

## 技術目標

### 正確性與安全性
- **記憶體安全**：透過 Rust 型別系統消除緩衝區溢位、use-after-free 和資料競賽
- **確定性**：無未定義行為；所有控制流與資源管理明確
- **行為對等性**：新系統必須處理舊系統的 100% 使用案例（無靜默功能喪失）

### 效能目標
| 指標 | Node.js（基線） | Rust（目標） | 改進 |
|---|---|---|---|
| 平均事件延遲 | 15 ms | < 2 ms | 7.5× |
| 95th-percentile 延遲 | 100 ms | < 10 ms | 10× |
| 記憶體佔用（空閒） | 80 MB | 25 MB | 3.2× |
| RSS 增長（每日，負載下） | ~2% | < 0.1% | 20× |
| 最大 GC 暫停 | 500 ms | 0 ms（確定性） | 無限 |
| CPU 使用（高峰，8 核 ARM） | 85% | 25% | 3.4× |

### 部署與運營
- 支持增量上線（Stage 0–4）含自動回滾
- 維持與現有 MQTT 用戶端和 REST API 消費者的向後相容性
- 減少運營負擔（監控、警報、手動重啟）

## 限制與風險

### 限制
1. **無破壞性 API 變更**：現有用戶端代碼必須繼續運作
2. **漸進式遷移**：無法強制所有客戶同時升級
3. **團隊專業知識**：團隊的 Rust 經驗有限；需要進度時間
4. **維護負擔**：轉換期間將維護雙系統（2–6 個月）

### 已知風險
1. **更長的開發時間線**：重寫需要 2–3 個月，而非快速修補 Node.js
2. **新工具鏈開銷**：構建系統、依賴管理、ARM 邊緣設備跨編譯
3. **測試負擔**：必須詳盡驗證行為對等性（golden-master 測試、負載測試、長時間浸泡測試）

## 考量替代方案

### 選項 A：「添加更多記憶體」（Node.js + 叢集模式）
- **方案**：執行多個 Node.js 進程，使用負載平衡器；添加快取與記憶體限制
- **優勢**：工程工作量低；利用現有代碼庫
- **劣勢**：
  - 遮掩根本原因；每個進程仍有記憶體洩漏
  - 增加每設備資源佔用（128 MB → 256 MB 或更多）
  - 無法解決尾部延遲問題
- **決策**：拒絕 — 臨時補丁，非解決方案

### 選項 B：「Go 或 C++」（替代編譯語言）
- **方案**：用 Go（學習曲線較淺）或 C++（最大效能）重寫
- **優勢**：Go 提供更快的進度；C++ 提供最大優化
- **劣勢**：
  - Go：仍有 GC（無法完全解決記憶體洩漏問題）；並行複雜性
  - C++：陡峭學習曲線，記憶體安全負擔仍在團隊身上
  - 兩者：IoT/工業協議生態系比 Rust 小
- **決策**：拒絕 — Rust 的記憶體安全保證與異步生態更符合目標

### 選項 C：用 Rust 重寫（已選擇）✅
- **方案**：用 Rust 完整架構重寫，以增量分階段上線
- **優勢**：
  - 設計上消除記憶體洩漏
  - 零成本抽象的效能
  - 優秀的異步/並行原語（tokio）
  - 豐富的 IoT 生態系（mqtt、serial 協議、跨編譯支持）
  - 團隊學習機會
- **劣勢**：
  - 更高的初期工程工作量
  - 團隊需要學習新語言
  - 更長的開發時間線
- **決策**：已選擇 — 穩定性與效能的最佳長期投資

## 成功指標

### Phase A（忠實移植）
- ✓ 與 Node.js 的 100% 功能對等（所有路由、MQTT 主題、資料格式）
- ✓ 行為對等性透過 golden-master 測試在 3+ 週生產流量重放上驗證
- ✓ 無新客戶面向的 bug 引入

### Phase B（強化與優化）
- ✓ 30 天連續負載下記憶體增長 < 0.1%
- ✓ 95th-percentile 事件延遲 < 10 ms（完整生產工作負載）
- ✓ 90 天現場試驗中零計畫外重啟
- ✓ 相同吞吐量下 CPU 使用量減少 ≥ 50%（相比基線）

### 運營
- ✓ 分階段上線無客戶阻礙事件完成
- ✓ 自動回滾觸發器預防延長停機
- ✓ 團隊有信心維護與擴展 Rust 代碼庫（培訓、知識庫、手冊）

## 範圍與時間表

### 範圍
- **包含**：核心閘道器平台（所有模組、所有 MQTT 用戶端、所有 REST API、持久化存儲、OTA 更新）
- **不包含**：Web UI 前端（現在保留 Node.js）、ML 推理後端（保留 Python）

### 預估時間表
- **Phase A（忠實移植）**：6–8 週（模組對模組移植 + golden-master 測試）
- **Phase B（強化）**：3–4 週（優化、負載測試、長時間浸泡驗證）
- **分階段上線**：2–4 週（Stage 0 → 4、自動化測試、客戶驗證）
- **總計**：3–4 個月端對端
