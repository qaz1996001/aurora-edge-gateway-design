# 問題陳述與目標：為何用 Rust 重寫 Aurora Edge Gateway？

## 執行摘要

**Aurora Edge Gateway** 是分散式工業 IoT 平台，負責邊緣設備上的實時感測器資料聚合、邊側計算和設備控制（部署平台：4 核 ARM Cortex-A53、標稱 4 GB RAM、OS 實際可用約 2.84 GB、無 swap）。原始 Node.js 實現雖然功能完整，但在生產環境中暴露出三個關鍵弱點：

1. **記憶體基線偏高**：16 個服務 / 8 個啟動階段的多進程架構，相對裝置可用 RAM 佔比偏高（實測：3 小時活躍負載下 1538 MB，約佔可用 2.84 GB 的 54%）
2. **CPU 開銷偏高**：高峰期感測器事件處理時 CPU 使用率偏高（實測：待機 52%、3 小時活躍負載 64%，4 核）
3. **Load average 偏高、餘裕不足**：同一多進程架構導致（實測：3 小時活躍負載下 4 核 load average 平均 3.30）

本文檔概述完全用 Rust 重寫的商業與技術理由、可量化的目標，以及權衡。

## 問題：Node.js 的瓶頸

### 症狀 1：記憶體壓力相對於可用 RAM 偏高
- **觀察**：16 個服務 / 8 個啟動階段的 Node.js 架構（實機約 20 個 OS 進程）在 3 小時活躍負載窗口下常駐 1538 MB，約佔 4 核 ARM Cortex-A53 目標平台（標稱 4 GB RAM、無 swap）可用 2.84 GB RAM 的 54%。開機至全服務上線約需 2 分 30 秒。
- **影響**：面對流量尖峰或未來感測器數量增長時，記憶體餘裕不足；約 20 個進程各自重複的開銷無法共享
- **根本原因**：
  - 每個 Node.js 服務各佔一個 OS 進程，使基礎執行環境／heap 開銷隨服務數倍增
  - Node.js 垃圾回收在逐進程基線之上再疊加 heap 開銷
- **目前基線（實測）**：3 小時活躍負載下 1538 MB（4 核 ARM Cortex-A53，約佔可用 2.84 GB 的 54%）；Rust 對照數字見 `02-architecture-overview.zh-TW.md` 與 `03-migration-strategy.zh-TW.md`（206 MB 全棧常駐，14 個受監督服務 + Python 子行程）

### 症狀 2：CPU 使用率與負載餘裕
- **觀察**：
  - 待機 CPU：52%（4 核 ARM Cortex-A53）
  - 3 小時活躍負載下 CPU：64%（4 核）
  - Load average：同一窗口下 4 核平均 3.30，距 4 核上限餘裕不多
- **影響**：面對流量尖峰或機隊增長時，並行感測器處理的餘裕有限
- **根本原因**：Node.js 事件迴圈與 V8 JIT 開銷，在約 20 個進程的架構下被放大，加上垃圾回收排程帶來的額外變動

### 症狀 3：多進程架構的運營複雜度
- **觀察**：16 個服務分布於 8 個啟動階段（實機約 20 個 OS 進程），須各自依序啟動、監控與重啟；垃圾回收時機在各進程內又增加排程上的不確定性
- **影響**：跨進程效能問題較難診斷；各進程內部也缺乏編譯期記憶體安全保證
- **根本原因**：動態執行環境、隱性記憶體管理、JavaScript 語義，加上逐服務一進程的部署模型

## 商業目標

### 主要目標
1. **降低記憶體佔用**：將 Node.js 逐進程架構（1538 MB、約 20 個進程、3 小時活躍負載）收斂為一組受監督的 Rust 服務，常駐記憶體大幅降低
2. **降低 CPU 與 Load average**：相對於 Node.js 基線（待機 52% / 活躍 64%，4 核 load average 3.30）降低穩態 CPU 使用率與 load average
3. **提升運營穩定性**：透過 soak 測試證明資源使用穩定、低漂移（目前驗證過最長連續運行為 10.6 小時）；不再因 GC 暫停導致連鎖失效

### 次要目標
1. **降低 CPU 開銷**：邊緣設備上功耗和熱負載降低
2. **簡化除錯**：確定性行為與編譯時檢查減少生產事件
3. **支持未來擴展**：為感測器數量增長做準備，無需重新設計

## 技術目標

### 正確性與安全性
- **記憶體安全**：透過 Rust 型別系統消除緩衝區溢位、use-after-free 和資料競賽
- **確定性**：無 GC 暫停；所有資源清理明確（deterministic drop 語義）
- **行為對等**：新系統必須處理舊系統的 100% 使用案例（無功能喪失）

### 效能目標
| 指標 | Node.js 基線（4 核 ARM Cortex-A53，3h 活躍負載） | Rust 目標／實測 | 說明 |
|---|---|---|---|
| **記憶體使用** | 1538 MB（約佔可用 2.84 GB 的 54%） | 206 MB 全棧常駐（14 個受監督服務 + Python 子行程），7.8h soak 實測 | 將逐進程開銷收斂為一組受監督服務 |
| **CPU 使用** | 待機 52% / 活躍 64% | 平均 6.3% / 峰值 8.8%，7.8h soak 期間零漂移 | 無 GC 暫停造成的抖動 |
| **Load average（4 核）** | 平均 3.30 | 平均 0.50 / 峰值 1.81（7.8h soak） | 餘裕充足 |
| **逐秒管線延遲** | 未單獨量測 | p95 56.4 ms，佔每秒預算約 5.6%，285 個樣本中 0 次超過 500 ms | 尾部延遲遠在預算內 |
| **延長 soak 驗證** | 無 | 目前最長連續運行：10.6 小時，PASS | 本專案沒有 90 天或數月級的連續運行資料 |

### 部署與運營
- 支持漸進式推出，搭配可靠的回滾路徑（二元切換 + 人工 SOP，各階段 5 分鐘內可回滾）
- 維持與既有 MQTT 用戶端和 REST API 消費者的向後相容
- 減少運營負擔（監控、告警、手動重啟）

## 約束與風險

### 約束
1. **無破壞性 API 變更**：既有用戶端程式碼必須繼續工作
2. **漸進遷移**：無法強制所有用戶同時升級
3. **團隊專業知識**：團隊 Rust 經驗有限；需要培訓時間
4. **維護負擔**：過渡期間需要維持兩個系統

### 已知風險
1. **較長開發時間線**：重寫需要持續的工程努力
2. **新工具鏈開銷**：構建系統、依賴管理、ARM 交叉編譯
3. **測試負擔**：必須詳盡驗證行為對等（golden-master 測試）

## 考量的替代方案

### 選項 A：「增加記憶體」（Node.js + Cluster）
- **方法**：執行多個 Node.js 進程搭配負載平衡器；添加快取
- **優點**：更低工程努力；利用現有程式碼
- **缺點**：
  - 遮掩根本原因；每個進程中仍存在洩漏
  - 增加裝置資源佔用
  - 無法解決延遲問題
- **決策**：拒絕 — 臨時修補，非解決方案

### 選項 B：「Go 或 C++」（替代編譯語言）
- **方法**：用 Go（更低學習曲線）或 C++（最大效能）重寫
- **優點**：Go 提供更快上手；C++ 提供最大優化
- **缺點**：
  - Go：仍有 GC（無法根本解決洩漏）
  - C++：陡峭學習曲線，記憶體安全負擔仍在團隊
  - 兩者：IoT 生態系比 Rust 小
- **決策**：拒絕 — Rust 的保證更符合目標

### 選項 C：用 Rust 重寫（已選擇）
- **方法**：完整架構重寫搭配漸進式分階段推出
- **優點**：
  - 設計上消除記憶體洩漏
  - 零成本抽象保証效能
  - 優秀的 async/並行原語
  - 豐富的 IoT 生態系
  - 團隊學習機會
- **缺點**：
  - 更高的前期工程努力
  - 團隊新語言培訓
  - 較長開發時間線
- **決策**：已選擇 — 長期穩定性最優賭注

## 成功指標

### Phase A（忠實移植）
- ✓ 100% 功能對等（所有路由、MQTT 主題、資料格式）
- ✓ 行為對等透過 golden-master 測試驗證
- ✓ 無新用戶面向漏洞引入
- ✓ 記憶體與 CPU 分析基線已捕獲，供 Phase B 比較

### Phase B（強化與優化）
- ✓ CPU 實測平均 6.3% / 峰值 8.8%（7.8h soak，相較 Node.js 待機 52% / 活躍 64%）
- ✓ Soak 期間記憶體增長可忽略；soak 測試中找到的唯一一次持續增長問題已修復（詳見 `04-testing-strategy.zh-TW.md`）
- ✓ 目前最長連續 soak（10.6h）通過，最後一段時間零重啟
- ✓ 延遲實測 p95 56.4 ms（約佔每秒預算 5.6%），0 個樣本超過 500 ms
- ✓ 團隊能獨立維護與增強

### 運營
- ✓ 分階段推出無用戶阻擋事件完成
- ✓ 二元切換回滾搭配有文件記錄的人工 SOP，各階段 5 分鐘內完成，防止持續中斷
- ✓ 團隊有信心維持與擴充 Rust 程式碼庫
